Proposal

Plainly

Kodi’s public API version numbers move without warning during a cycle — sometimes in the last days before gold. This pins each number to a cut, so anyone writing against Kodi knows what version 22 will present long before it ships.

Substance

  • Breaking changes land before Beta 1. Additive changes close at RC1. After RC1, patch only.
  • Kodi 22 presents JSON-RPC 14.x, Python 3.x, skin 5.x, Game add-on API 8.x.
  • ADDON_API is fully determined by the cut — 21.90.80n beta, 21.90.90n RC, 22.0.0 gold.
  • The schedule is a checked-in manifest, so CI rejects a bump past the ceiling rather than a reviewer catching it.

01The problem

A third party cannot presently predict which API version a Kodi release will present, because the number has moved at a different point in every cycle.

The JSON-RPC contract is the clearest case. Across four cycles the major component has landed at gold, landed two minors past a major at gold, never landed at all, and landed mid-beta:

CycleBeta 1RC1ReleasedWhere the major landed
v19 Matrix11.19.111.21.112.2.0After RC1, plus two minors
v20 Nexus12.10.212.10.213.0.0At gold
v21 Omega13.3.013.5.013.5.0Never
v22 Piers13.11.0—14.x12 Aug 2026, two months after Beta 1

Binary add-on APIs behave the same way. In this cycle the Game add-on API moved 6.0.0 → 8.0.0 across five bumps between 12 and 26 August, all after the Beta 1 cut, with ADDON_INSTANCE_VERSION_GAME_MIN moving in step — so every game client binary built against Beta 1 is refused by the current master.

None of these bumps was wrong on its own terms. The defect is that they are unannounced: an author who compiled against Beta 1 had no way to learn that the floor would move under them, and no document to read that would have said so.

02The ladder

Each cut closes one component of every public API version. Nothing that is closed reopens for the life of the release.

From this cutMajorMinorPatchWhat may still land
Alpha openopenopen Anything, including breaking changes
Beta 1 lockedopenopen Additive API only. No signature, semantic or floor change
RC1 lockedlockedopen Fixes to declared behaviour. No new surface
Gold and point releases lockedlockedopen Fixes only, for the life of the branch

Locked means the component may not change, in either direction. A minor bump after RC1 is a rejected pull request, not a discussion; the change waits for the next cycle’s alpha.

Compatibility floors

A _MIN in versions.h, or a backwards-compatibility abi in an addon.xml, is the actual promise to a compiled add-on. It follows the major: locked from Beta 1. Raising a floor after Beta 1 invalidates every binary built against that beta and is the one change the ladder exists to stop.

One override exists. A release manager may move a locked component to fix a defect that would otherwise ship, by recording it in the manifest with a reason. The record is the point — an override is visible to everyone reading this page, rather than discoverable only by diffing a header.

04What you can rely on

If you write against Kodi, these four lines are the whole document.

  • JSON-RPC clients. Kodi 22 speaks 14.x. Methods and fields may be added up to RC1; nothing declared is removed or changed in shape.
  • Python add-ons. Kodi 22 presents xbmc.python 3.x with an unchanged 3.0.0 floor. An add-on importing 3.0.0 loads on every v22 build, beta included.
  • Skins. Kodi 22 presents xbmc.gui 5.18.x against a 5.17.0 floor.
  • Binary add-ons. Build against Beta 2 or later and your binary loads on 22.0 gold, because no _MIN moves after Beta 1. Beta 1 itself predates this schedule — Game clients must rebuild.

The reciprocal obligation is on the release: any of these lines proving false is a release blocker, not a release note.

05Enforcement

The schedule is only worth publishing if a pull request cannot quietly break it, so the numbers above live in the tree in a form CI reads.

A single manifest, api-versions.json, sits beside version.txt. Each entry names where a version is read from, the major the release has declared, and the value as of the last cut:

{
  "release": { "major": 22, "codename": "Piers" },
  "surfaces": [
    {
      "id":       "jsonrpc",
      "path":     "xbmc/interfaces/json-rpc/schema/version.txt",
      "read":     "key:JSONRPC_VERSION",
      "line":     "14",
      "declared": "14.2.0"
    },
    {
      "id":       "python",
      "path":     "addons/xbmc.python/addon.xml",
      "read":     "xml:/addon/@version",
      "line":     "3",
      "declared": "3.1.0",
      "floor":    "3.0.0"
    },
    {
      "id":       "addon.game",
      "path":     "xbmc/addons/kodi-dev-kit/include/kodi/versions.h",
      "read":     "define:ADDON_INSTANCE_VERSION_GAME",
      "line":     "8",
      "declared": "8.0.0",
      "floor":    "8.0.0"
    }
  ]
}

Three readers cover every current surface — key: for the whitespace-separated version.txt files, xml: for an addon.xml attribute, define: for a string macro in versions.h. A surface that needs a fourth is a surface that should be reporting its version differently.

What the check does

  • Reads VERSION_TAG from version.txt to determine the phase — alpha, beta, RC or release — and from that, which components are locked per §02.
  • For each surface, fails if the major differs from line; if a locked component differs from declared; if floor has moved while locked; or if the value has gone backwards.
  • Validates ADDON_API and VERSION_CODE against the cut table in §03, which is derived, not declared.

Re-baselining declared is the act of cutting a release. It runs on the cut commit and nowhere else, which makes the release manager the only person who can move a locked number, and makes each move a reviewable one-line diff.

The check needs the merge base, the working tree and nothing else — no build, no network. It belongs wherever the cheap per-PR checks already run.

06Non-goals

  • Internal schema versions are out of scope. Video, music, texture and add-on database versions are not third-party contracts and are not scheduled here.
  • This does not redefine semantic versioning for any surface. It says when each component may move, not what it means.
  • It is not retrospective. v21 and earlier are cited as evidence only. v22 is scheduled from its Beta 1 baseline forward, with the two surfaces that already moved past it — JSON-RPC and Game — declared rather than reverted.
  • It does not set release dates. Cuts are named, not scheduled; the numbering holds whenever a cut happens.
