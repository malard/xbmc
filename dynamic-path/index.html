GetPath and GetDynPath

The dynamic path holds whichever resolution step last wrote to it, and falls back to the item path without saying so. Call sites ask four different questions of two accessors, and recent fixes move them back and forth between the two.

Plainly

A library item, a plugin item or a Blu-ray has a name it is listed under and a different thing that is actually played. Kodi keeps the second in one undocumented field, and each place that needs "the file" has to guess which of the two to read. The guesses keep getting changed, and each change fixes one kind of item.

Substance

  • m_strDynPath has no documented meaning; its writers give it eight different ones.
  • GetDynPath() returns m_strPath when the field is empty, so a wrong choice never fails visibly.
  • Callers need four answers: what to open, where the file is, what the library knows it as, what to show.
  • Six recent PRs change call sites in both directions, each tested against one producer.

01The two accessors

GetPath() is the item's identity. GetDynPath() is m_strDynPath if set, otherwise m_strPath.

MemberDocumented as
m_strPath"complete path to item" (FileItem.h:589)
m_strDynPathnothing (FileItem.h:590)
GetDynPath()nothing; falls back to m_strPath (FileItem.cpp:1759)
HasDynPath()nothing; the only way to tell "resolved" from "fell back"

GetURL() and GetDynURL() (xbmc/xbmc#27085) are parsed views of the same two strings and carry the same ambiguity.

A widget item goes from videodb:// to the file; a Blu-ray in a stack goes from the stack to a playlist. After either, nothing records the earlier steps.

03What callers need

Call sites ask four questions. Two accessors answer them.

QuestionUsed forRight answer
What does the player open?input streams, redirects, Blu-ray navigationthe last resolution step
Where is the file?subtitles, NFO and art beside it, 3D name, thumbnailsthe real file; never videodb://, bluray:// or a resolved stream URL
What does the library know it as?bookmarks, video settings, stream details, play countsthe path the database stores
What does the user see?labels, logsusually neither

For a plain file all four answers are the same string, which is why most call sites work whichever accessor they use.

By reading

After #29584, 3D detection matches the regular expressions against whatever the field holds. For a library file that is the file name. For a plugin it is the resolved URL, and for a Blu-ray played through a playlist it is a bluray:// path. Not reproduced in a running Kodi.

05How bugs get through

  • The fallback hides the choice. Reading the wrong accessor returns the other path rather than nothing, so tests built on a plain file pass either way.
  • One field, many meanings. Section 02 lists eight. A change is tested against the producer in the report, not against the other seven.
  • Layers overwrite each other. Code that needs an earlier step, such as the real file behind a Blu-ray playlist, can no longer get it.
  • Copies can drop it. Any copy or merge that misses the field reverts the item to its listing path; #28874 fixed one.
  • It is used as scratch. The NFO export points it at a file that is never played.

Whether GetDynPath() should keep falling back to the item path, or callers should test HasDynPath(). Whether a stack or a Blu-ray playlist counts as "the file" for subtitles and art.

07Not in scope

  • Database path storage. The files and path tables stay as they are; section 03 only names which of them a caller should read.
  • Music. The same field is set in two music sites; the video cases are where the reports come from.
  • Reverting any merged change. Section 04 records direction, not error.
