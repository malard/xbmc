Kodi/ Architecture proposal/ Draft

Playlists, entries and players

Kodi has no single answer to what is playing and what is playing it, so every part of the application works it out for itself, from whatever source is nearest.

Plainly

A remote control asks Kodi what is playing. Different parts of Kodi answer differently, because each works it out from a different place at a different moment. Kodi only ever renders two things, video and audio. This gives each a playlist that always exists, one place that knows what each is doing, and lets everyone else ask it.

Substance

  • A playerid has named the current playlist, not the player, since 2015.
  • A playlist type is not a type: it selects one of two hardcoded members.
  • What an entry claims is static. What is rendering is state. One number carries both.
  • All twenty Player.* methods require an id the application itself has never needed.
  • CPlayListPlayer is an index store the application drives from outside, and the current item is held in five places.

01The questions

QuestionNature
What is playingthe entry
What kind of playback it isa classification, which decides what controls to offer
Where it came froma playlist and a position
What phase it is inrequested, opening, streaming, paused, ended, failed
What it containsaudio, video and subtitle streams

The askers are not one client: JSON-RPC, Python add-ons, the GUI info layer and skins, the UPnP renderer, AirPlay, CEC, the OSD, the slideshow, party mode, and the playlist player itself. Consistent has to mean consistent across all of them.

02History

Three defensible steps and one deliberate inversion.

WhenWhatEffect
2010 Players addressed by media type name, in AudioPlayer.*, VideoPlayer.*, PicturePlayer.* One player core and one playlist per media type. Player identity and playlist identity were the same question.
2011-08-31
c4f161e177		 The three namespaces merge into Player, "accessed by a unique ID" GetPlaylist(PlayerType) is a constant switch. The identity is correct. The debt taken on is spelling the constants with the PLAYLIST_* values, because the numbers matched.
2015-03-05
200e60df99		 "Keep playlistid=playerid in JSON interface" The constant switch becomes a live query of the current playlist, and GetPlayer gains a round-trip check against it. From here an id names the playlist, and a correct id can resolve to nothing.
2024-05-10
f5a84bc31f		 PLAYLIST::Id becomes an enum class The borrowing hardens into the type system: a playerid is now typed as a playlist id.

The 2015 change fixed a real complaint, that two numbers clients treated as interchangeable had stopped agreeing. Faced with an invariant coming apart, it kept the invariant and gave up the identity. Everything it protected assumed one player core and one playlist per media type. Since then VideoPlayer absorbed audio playback, party mode went mixed, PVR arrived with radio channels carrying video, and a bluray:// path is classified as neither video nor audio, so a disc belongs to no queue at all and the id a client sees comes from the guess.

03Current state

Three partial sources, no reconciler, and every consumer picking one.

Known issues today

ObservedBecause
A remote enumerates a video's audio streams correctly and cannot switch any of them. A video played from the music playlist is published as playerid 0. GetProperties serves video and audio from one branch so the menu is right, but SetAudioStream is not served for the audio player, and playerid 1 fails the round-trip against the playlist and resolves to nothing.
Enabling video party mode advertises a player id that its own methods reject. The announcement is made in the same call that asks for playback, before the player has opened anything, so the player still answers for the previous file or for none.
Playlist.Add on playlistid 2 succeeds and the items are gone. Ids 2 and 3 have no storage. They resolve to a shared list that is cleared on every access.
Pausing costs two calls, the first of which is the one that answers wrongly. All twenty Player.* methods require playerid, so a client must call Player.GetActivePlayers and hand the id back before it can do anything at all.
Shuffle and repeat changes carry a playlist id in the playerid field. CPlayListPlayer stamps its own id into a player notification.
A radio channel carrying video is published as two players at once. IsPlayingVideo() is true because video is decoding and IsPlayingRadio() is true because it is a radio channel, so both bits are set and one playback is published as two players. The notification for the same playback says 0, because the announcement manager rewrites the id from radio or TV.

Where the id comes from

There are two playlists. CPlayListPlayer holds m_PlaylistMusic and m_PlaylistVideo as members; TYPE_PICTURE and TYPE_GAME resolve to a shared scratch object that is cleared on every access, so anything added to playlist 2 is discarded the next time anyone reads any unrecognised id. The playlist does nothing with its own type: CPlayList::m_id is read in three places, all of them stamping playlistid into an announcement.

CPlayListPlayer does not drive playback. CApplicationMessageHandling does: it calls PlayNext when a file ends, and for a gapless successor it takes the next index, holds it in the application, and writes it back into the playlist player when the file starts. The current item is therefore kept in five places - CApplication::m_itemCurrentFile and m_nextPlaylistItem, CPlayListPlayer::m_iCurrentSong, CGUIInfoManager::m_currentFile and CApplicationStackHelper::m_currentStackPosition - written at different moments for different readers.

04Failures

FailureConsequence
No authorityEight derivations that disagree, and nothing to appeal to.
No valueA playerid is typed PLAYLIST::Id. The contract says it names a player; the type says it names a playlist. A holder cannot tell which it has.
No lifecycleEvents are emitted at implementation moments, not transitions any object owns, so a consumer must ask elsewhere what the state is, inside an interval nobody wrote down.
Static question, dynamic answerIsPlayingVideo() means "has the decoder got video up". Consumers use it to mean "is this a video". They agree only after streams open: while a file is opening the demuxer has not reached the video stream, so it returns a confident false.
Many producers, delayed deliveryPlayers, the playlist player, party mode and the slideshow each publish; the announcement manager rewrites afterwards; delivery is deferred to one low-priority thread, so a consumer that reads live state on receipt reads a different moment from the one described.
A target where none is neededEvery Player.* method requires a playerid. The application's own control surface, PlayerControl, has taken a verb and nothing else since 2010.

The root is the last one. playerid is a classification pretending to be a handle - there are not three engines, video and audio are one object classified by what it opened, and picture is a window - and the only reason anything has to classify it at all is that the API asks a client to name a target. Every derivation in the table above exists to answer a question that should not be asked.

05Proposal

Kodi renders two things, video and audio. Whatever is playing holds one or both, and that is the only classification anything needs.

PieceOwns
EntryOne position in a playlist: the item, a stable id that is never reused, and a repeat mark. Which side it is on is what it claims; nothing classifies it after the fact.
CPlayListThe entries, its own lock, its cursor, its shuffle, its wrap, and a queue of play-next requests. It makes its own edits and says so afterwards. No type. Never reordered.
IPlayListShuffleWhat follows an entry, and what precedes it. CPlayListNoShuffle when shuffle is off, CPlayListRandomShuffle when it is on. A playlist always has one.
CApplicationPlayListsThe Video playlist and the Audio playlist, which always exist. The phase of each - idle, playing, paused - and whether Audio is following Video. Everything published comes from it. It replaces CPlayListPlayer.

While a file is opening there are two answers and both are true: the entry claims Video, and nothing is rendering yet.

A stack is one entry whose parts are internal. A gapless successor is the next entry. A direct play is a playlist of one, replacing whatever that side held. Each of those carries its own special case today; none of them needs one here.

Publishing. The current site derives the id from the playlist, and guards on a player that may still be describing the previous file.

After

void CPartyModeManager::Announce()
{
  // the component stamps the entry, the side, what it holds and the phase
  components.GetComponent<CApplicationPlayLists>()->Announce(PlayerProperty::PartyMode, m_bEnabled);
}

06Two sides

PlayingHolds
Music, a radio channelAudio
A film, an episode, a TV channel, a gameVideo and Audio
A picture slideshowVideo
A radio channel that turns out to carry videoAudio. Whoever put it there said so; if it belongs on Video that is their call to make in advance, not the playlist's to make afterwards.

Two things run at once only when what they hold does not overlap, which in practice is music under a slideshow. A new claim displaces whoever holds that side. That is what Kodi does today, written as special cases.

RuleMeaning
Each side always has a playlistPossibly empty. Queueing before anything plays works as it does now. Whether anything is playing is the phase, not whether a playlist exists.
Audio follows VideoWhen something on the Video side also holds Audio, Audio follows it for the duration. The Audio side's own playlist is kept and handed back when the film stops - stopped, not resumed, as today. It is the only takeover there is, so it is one flag.
The setter decides the sideThe music library puts entries on Audio, the video library on Video, a smart playlist by its type, PVR by TV or radio. The playlist never classifies what it holds. Where a caller names nothing - a bare Player.Open of a path - the choice is made once, at the edge.
A verb names a sideVideo or Audio. With neither named it goes to both when they differ, and once when they are the same playlist.
No special cases for a bare verbA bare toggle flips each; a bare Next advances both. A caller that cares which names its side. Kodi's own GUI actions are callers like any other, and know which window has focus.

07What plays next

Decided inside the playlist, so it can be tested with no application, no player and no GUI.

Asked, in orderAnswer
The first queued play-next requestThat entry, and carry on from there. Consumed when used, dropped if its target has been removed. A new item asked to play next is inserted after the current entry, or after the last such insert.
The entry's repeat markPlay this entry again. A user skip leaves this step out, so a marked entry can always be left; the mark stays until cleared.
IPlayListShuffleWhat follows this entry in play order.
The playlist's wrapNone, to the start, or to a named entry.

Repeat one and repeat all stop being two values of one setting: the first is a mark on an entry, the second the playlist's wrap. The primitives each do one thing - SetRepeat(entry), ClearRepeats(), SetWrap(...) - and the three-state button is composed once, on CApplicationPlayLists: clear everything, then mark the current entry or set the wrap. A sequence that plays through and then holds on its last slide is expressible; the stock GUI has no need to show it, and an add-on can drive it. A repeating entry that will not play stops playback, as now.

Party mode becomes a feeder: when an entry starts it tops the list up to ten ahead, adding at the end. It never removes, moves or fixes an index, and when it ends it clears the playlist.

Looking is not moving. A skin's "up next" label and a player queueing its gapless successor ask what would follow; the cursor moves when that entry actually starts.

Shuffle

The stored list keeps the order it was built in. Shuffle is a routine behind IPlayListShuffle that answers what follows and what precedes an entry, and nothing else. It is told of every change to the list - which entry was added, removed or moved - and decides for itself whether to act. There is no unshuffle: turning shuffle off installs CPlayListNoShuffle, and the current entry is where it always was. A presenter that wants the play order - the now-playing window, a remote's queue tab - asks for a sorted view, built by walking the shuffle from the current entry, and read-only.

Uniform random clusters, which is what listeners report as "not random". A routine that spreads artists, or is seeded and reproducible, is a further class inheriting the same interface, written without touching any of this.

Entries have ids

Every consumer today addresses a playlist by integer position, and the playlist player exists largely to keep one such integer honest across edits. An entry's id survives any edit and resolves to nothing once the entry is gone, so the cursor, a play-next request, an end-rule target and a remote naming an entry are all the same kind of reference. Position is derived when asked for. MPD has worked this way for twenty years: play and playid, delete and deleteid.

08Playlist queries

Removing the type does not make a playlist mute. It makes its answers derived rather than declared.

Asked of a playlistAnswer comes from
Is this one kind of content, or hybridthe union of what its entries claim
What does it currently containcounts per kind over the entries
What is current, and where is itthe cursor; the position is derived from it

Kodi answers where answering is practical, and what it answers has to be accurate rather than exhaustive. A consumer holding accurate counts can compose whatever else it needs on its own side of the boundary.

Constraint

These answers are computed from the entries and are read-only, so they cannot disagree with the contents. They inform presentation. They never decide what an entry claims - that stays with the entry.

09Publishers, before and after

The slideshow also subscribes, so it receives its own notifications.

PublisherPublishes todayAfter
CApplicationMessageHandling Every Player.On* event. Each site sets the id from the current playlist. It also drives the playlist player from outside: PlayNext on ended, and the gapless index written in on started. The same events, none of them setting an id. It asks the playlist for the next entry and opens it.

10What goes

RemovedBecause
CPlayListPlayerOf 40 methods and 19 message cases, 7 and 18 are already plain forwarding, and 15 more become so once the playlist owns its edits, cursor and shuffle. The rest is one job, the current playback, which moves to CApplicationPlayLists. Its transport messages already name no player; they move to the application.
Five copies of the current itemm_itemCurrentFile, m_nextPlaylistItem, m_iCurrentSong, the info manager's m_currentFile, and the stack helper's position as a rival cursor. One record, handed to whoever needs it.
PLAYLIST::Id, TYPE_MUSIC, TYPE_VIDEO, TYPE_PICTUREThey were standing in for the two sides. Inside Kodi nothing names a playlist by number.
playlist_type_hintIt carried, as a string property, the one fact its writers already knew: which queue. Now they put the entry on that side.
ReapSongs, MovePlayingParty mode pruned and reordered the list to keep the current song at index 0. With a cursor that is not an index there is nothing to keep.
UnShuffle(), and the order number written onto each itemThe list is never reordered, so there is nothing to undo.
The playlist-edit messages and wrappersCPlayList locks itself, as CFileItemList and most of the tree do, so an edit no longer has to be marshalled onto the application thread.
RepeatStateReplaced by the entry rule and the end rule.

11What changes for a client

An old call still does what its caller meant, because the verb does. Nothing is carried for its own sake.

SurfaceWhat happens
A target on a verb Video, Audio, or nothing. A bare Player.Stop stops everything.
playerid and playlistid An interface-boundary matter only. If the API keeps accepting them, 0 becomes Audio and 1 and 2 become Video, once, at the edge.
A playerid in a notification Not published. players says what the playback holds and item says what it is.
Player.GetActivePlayers Removed. Its purpose was to vend an id to hand back, and nothing hands an id back.
When The boundaries are their own piece of work, after the core has landed. Until then each is patched to keep today's behaviour, or left knowingly broken and said so.
Entries Gain an id. Position-based calls stay; an id-based form beside them cannot go stale.
Shuffle Playlist.GetItems returns the list as built whether or not shuffle is on. What follows the current entry is a question, not the next row.
Event moments Unchanged. Player.OnPlay keeps firing on the starting edge, because what it describes is known before anything opens.
Python onPlayBackStarted keeps its name and its moment, and carries what the entry claims. xbmc.PlayList.unshuffle() goes with the concept.
The schema Removing a required field from Player.Notifications.Player, and a required parameter from twenty methods, is breaking. It is a version bump, and it is the point of the exercise. The JSON-RPC vocabulary around it is open to a clean-up at the same bump.

12Non-goals

Named as decisions, so they are not read as oversights.

  • Not touching the player engines. IPlayerCallback already reports every transition this needs. CVideoPlayer loses four announcement sites and nothing else.
  • Not changing when notifications fire. The identity problem is solved by where the answer comes from, not by moving the moment.
  • Not renaming Python callbacks. Add-ons bind to them by name.
  • Not touching player core selection. Which engine opens a file is a separate decision from what it holds.
  • Not touching PVR. A channel is a direct play on the side PVR puts it. Channel navigation, the EPG successor and CPVRPlaybackState stay as they are. Radio that carries video is xbmc/xbmc#29211, and is the setter's call.
  • Not rebuilding the slideshow. Its publishing moves; its slides becoming entries is later work.
  • Not designing smarter shuffles. The interface is here; the routines are later work.
  • Not moving the file-format loaders out of CPlayList. Nine subclasses make it both the live queue and a parser. Acknowledged, and left for its own change.
  • Not a rename sweep. New names follow the CPlayList family; existing ones are normalised only where a change already touches them.
