JSON-RPC API strategy

The API grew one method at a time, wherever the code happened to live. This is the shape it is rebuilt to: every namespace names what it acts on, and every target reads, writes and announces its state the same way.

Plainly

Kodi's remote-control API is used by web interfaces, apps, add-ons and, increasingly, AI that writes bespoke interfaces for people. It is being reorganised so that anything written against it can guess where a thing is, what it will do, and why it failed.

Substance

  • A namespace is the target acted on: Player is whatever is seen or heard right now.
  • Each target has GetProperties, partial SetProperties, actions, and one OnPropertiesChanged.
  • Library items are targets too, with ids that are never reused.
  • Errors carry declared reasons; asynchronous completion is declared; TCP and WebSocket never block.

01Consumers

"Going forward it will be AI, but it's mainly used for web interfaces, addons and apps, there is no human consumer."

AI already drives the API for testing and development, and will build "bespoke interfaces for each user's bespoke requirements". Two roles follow: the operator, which calls the live system, and the author, which writes a client from the published description alone.

Existing clients (Kore, Yatse, Chorus, Home Assistant, add-ons) "will get patched"; compatibility is not a constraint. The layer reports what the application knows and does not work things out itself (2026-09-05).

03Player

"A general space for anything you are actively seeing or hearing right now, in the abstract."

  • Volume, mute, audio delay and view mode belong here and work with nothing playing.
  • A call may name a target playlist to disambiguate, for a slideshow running over music. "If you don't need to state it, don't force it": the target is optional, and methods where it means nothing do not take it.
  • With no target named, verbs act on everything playing and succeed if any does; queries answer for the playback, then the slideshow.

04Properties and actions

Every target has GetProperties, SetProperties and action methods.

  • SetProperties is partial: a property not named is untouched. It answers with the values in force, so a clamped or refused change is visible.
  • "For complex actions they can have their own setter and getter, but they are in the minority and far more uncommon to be called anyway."
  • Read-only properties are marked readOnly in the target's property schema.

A property is state set to an absolute value, where setting it twice equals setting it once (volume, speed, repeat, time). Relative changes and events are actions: "separate action for stepping", so volume up is Player.VolumeUp, not a relative value in SetProperties.

05Notifications

Every state change is <Target>.OnPropertiesChanged, carrying only what changed, under the names GetProperties uses. Pause is speed becoming 0; a volume change is Player.OnPropertiesChanged. Only true events keep their own notification: OnPlay, OnStop, OnAVStart, OnPlaybackFailed, scan finished, OnQuit.

06Errors

Every error carries error.data with a stable machine-readable reason (nothing-playing, not-seekable) and the target concerned. Each method's schema declares its reasons beside the statuses it already declares. Today only InvalidParams fills error.data.

07Library items

A library item is a target, addressed by kind and id.

  • Its properties are read and written through GetProperties and SetProperties; changes arrive as that item's OnPropertiesChanged. This replaces the per-kind Get*Details and Set*Details families and VideoLibrary.OnUpdate.
  • Each library has one query taking the kind, filter, sort, limits and properties. "Keep the original ones as wrappers with preset values": GetMovies, GetRecentlyAddedMovies and the rest stay, each a preset over the query.

08Identity

"We should change to autoincrement and promise." Library tables move to SQLite AUTOINCREMENT, and the API promises an item id is never reused.

Today SQLite reuses max(rowid)+1, so a stored id can later resolve to a different item with no error. Nobody chose this: the schema predates the 2009 import, and the MySQL backend already appends auto_increment.

09Names

camelCase throughout: every property, parameter and enum name. Today 651 names run lowercase together (musicbrainzalbumartistid), with camelCase, snake_case and PascalCase outliers.

10Documentation

  • The schema is the source. It generates the OpenRPC and AsyncAPI documents, which api.kodi.tv publishes; that pipeline exists.
  • No tests check prose.
  • A method that completes later declares, as structured data, the notifications that complete it: Player.Open completes with OnAVStart or OnPlaybackFailed.

Open

Consequences drawn, not yet ruled on: responses on one connection may arrive out of order and are matched by id, as JSON-RPC 2.0 allows; a call that raises a dialog returns at once and completes through a declared notification.

12Open and out of scope

  • Delivery. "One atomic change, or as close to." The epic is flattened, then cut into reviewable pieces for master; slicing is not a design constraint.
  • Out of scope. Reorganising the application code behind the API, deferred to a later discussion. Typed parameters: not a goal, and no C++ is generated from the schema.
